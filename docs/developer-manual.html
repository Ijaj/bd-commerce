Developer Manual

How the bd-commerce backend is built, what it stores, and how data moves through it. Written for a developer who needs to understand the system quickly. The database reference (section 5) is generated from apps/api/prisma/schema.prisma, so it matches the code.

1. System overview

apps/api

NestJS 11 + Prisma 7 + PostgreSQL 18. The only thing that touches the database. REST under /v1, Swagger at /docs.

apps/admin

Staff admin panel. Vite + React 19 + Mantine 9 + TanStack Router/Query. Port 5173.

apps/portal

Partner portal for SR (sales reps). Same stack. Port 5190.

apps/shop

Customer storefront. Next.js 16, English at /, Bangla at /bn. Port 3100.

packages/*

api-client (typed fetch from OpenAPI), i18n (money/number/BN helpers), ui (design tokens and shared components).

infra/dev

Compose stack: Postgres 18, Redis 8, Garage (S3), imgproxy, Mailpit.

StoreHolds
PostgreSQLAll business data (80 tables, see section 5). Extension pg_trgm for fuzzy search; full-text search for the storefront.
RedisSettings cache (5 min, invalidated on write), login throttles, OTP/lock counters, scheduler lock (lock:job:*). Nothing here is the source of truth; flushing Redis loses no business data.
Garage (S3)Uploaded image files. Postgres keeps only metadata (media). Images are served through imgproxy (signed URLs, WebP).
MailSMTP (Mailpit in dev): new-device alerts, PO emails, OTP fallback in dev.

pnpm biome ci .                       # lint/format

3. Conventions that explain the data

ConventionDetail
MoneyInteger paisa (100 = ৳1). Columns end in _p (price_p, grand_total_p). Never floats. @bdc/i18n formatPrice() renders it.
PercentagesBasis points: 1500 = 15%. Columns end in _bp / Bp (VAT, SR commission, percent coupons).
IDsUUID v7 (time-ordered) for most tables. Geography uses fixed integer ids (upazilas 1001+ for Dhaka thanas). Human numbers (order, shipment, invoice, return, PO, memo) come from Postgres sequences: YYMM-NNNNN for orders.
NamingPrisma models are PascalCase; tables and columns are snake_case via @@map/@map. Timestamps are timestamptz.
Bilingual textPairs name_en / name_bn (BN optional, falls back to EN). Settings that show in the shop hold {en, bn} objects.
SnapshotsOrders copy title, SKU, price, discounts, address text and invoice print data at placement, so later catalog edits never rewrite history. order_items.image_media_id has no FK on purpose.
LedgersMoney and stock histories are append-only. Corrections are new rows (reversal/adjustment), never edits.
Soft statedisabled_at, archived_at, revoked_at, is_active. Rows with history are archived, not deleted (FKs are mostly RESTRICT).

4. Authentication and access

Staff (admin + portal)

  1. Email + password (Argon2id) → creates staff_sessions row, cookie bdc_staff_session (only the hash is stored).
  2. 2FA: TOTP (secret encrypted with STAFF_TOTP_KEY), replay guard via totp_last_step, 10 one-time backup codes (hashed). Until mfa_verified_at is set, only 2FA endpoints work.
  3. Throttle in Redis: 5 failures per email and 30 per IP per 15 minutes.
  4. New device (cookie bdc_staff_device fingerprint not in staff_known_devices) → email alert.
  5. Idle timeout 8 h by default (setting staff_session_timeout_min, per-staff override), absolute cap 7 days.

Permissions (RBAC)

Permissions are defined in code (apps/api/src/auth/permissions.ts) and synced into permissions at boot. Roles are rows; a staff member may hold several roles and gets the union. The Owner role is a system role: always every permission, cannot be edited or deleted, and the last Owner cannot be removed. A staff member can only grant permissions they hold (rule Q65). The admin sidebar hides items the user lacks permission for; the API enforces the same permission on every endpoint.

Customers and guests

Customers sign in with phone or email + password, SMS OTP at signup/reset (otp_codes, HMAC-hashed, escalating lock). Guests keep a bdc_vid visitor cookie that owns a cart; the cart merges into the customer cart on login. Guest COD orders above a threshold need an OTP; limits per phone/IP/day apply (guest_orders setting). Linking a guest order to an account requires a verified phone/email.

7. How data moves: the main flows

Placing an order (COD)

cart→quote→place (idempotent)→order + items→reserve stock→risk check
  1. Quote: evaluates prices (base → sale/flash, lowest wins) → auto coupons → at most 1 typed code → delivery charge from the zone. Nothing written.
  2. Place, one transaction: insert orders + order_items (frozen snapshot), payments row (method cod), order_status_history, stock reserved += qty with a stock_movements row (order_reserve), coupon redemptions, flash qty_sold. Idempotent on a client key so double-clicks do not duplicate.
  3. Risk (RiskService): sets risk_score, risk_reasons (velocity by phone/IP/device, COD above threshold, first guest order) and call_status = pending when risky. Never blocks the order.

Order status

processing→partially_shipped→shipped→delivered→completed

Side states: on_hold, cancelled, pending_payment (unused until online payments). on_hold/cancelled/pending_payment are set explicitly by staff; processing → delivered is derived from shipments by recompute(). delivered → completed happens in the complete-orders job after the return window. Cancelling releases reserved stock and reverses coupon uses, flash stock and bulk-code use; it is refused while a shipment is booked.

Shipping

Staff create shipments from order lines (split allowed) → pending → ready → book a courier (adapter writes courier_bookings with raw request/response, sets consignment_id) → handed_over → in_transit → delivered/failed/returning/returned. Status arrives by webhook or by the sync-couriers job and is stored in courier_status_events (raw and mapped). Stock leaves on handover (ship movement: on_hand -= qty, reserved -= qty). The delivery charge sits on the first shipment sent. Adapters: fake (works), steadfast and pathao (unverified against sandboxes; keys come from env, not DB).

Returns and refunds

requested → approved|rejected → pickup_booked → received → inspected → closed. At inspection each line gets a condition (resellable/damaged) and may restock (return_restock movement). A refunds row is created per refund: per-line amount = (line total − line discount) pro rata. Amount above returns.refundApprovalAboveP sets needs_approval and a different staff member holding refunds.approve must approve. Refunds are recorded only (no payment gateway or wallet ledger yet).

SR (field sales) and B2B

SR creates a memo (sr_sales, status submitted) for a buyer shop with SR-entered prices. Office staff approve (stock reserved, sr_reserve) or reject; on delivery stock ships (sr_ship) and a sale_due ledger row adds to the shop’s due; collections are recorded by the SR and confirmed (or rejected) by staff. Reversal posts a reversal row and restocks. Monthly sr_commissions = confirmed collections × rate (SR override or setting sr_default_commission_bp); clawbacks are sr_commission_adjustments.

Purchasing

draft → sent (lines locked, emailed to supplier) → partially_received → received, or closed (close-short) / cancelled. Receiving (purchase_orders.receive) records good and rejected qty per line (never more than remaining). Only good qty is stocked (po_receive movement), updates variants.cost_p by weighted average (before/after kept in po_receipt_items) and adds a receipt row to supplier_ledger. Payments and adjustments are further ledger rows; mistakes are reversed, not edited.

Promotions

Price order: base → sale price or flash price (lowest) → automatic coupons (priority order, must stack with each other) → one typed code (a second only if both allow stacking) → delivery discounts. Flash quantities are capped per item and per customer; the cart refuses more (409 FLASH_LIMIT). Bulk sale writes variants.sale_* and records old values in sale_batch_items so “Undo” restores them.

  2. prisma migrate dev hangs without a TTY. 12. Known gaps

  • Only COD is live. No gateway, no wallet/points/referral ledger yet (settings toggles stored, unused).
  • Steadfast/Pathao adapters untested against real sandboxes (no merchant accounts yet).
  • No audit-log table: only 2FA reset is recorded on the staff row. Order, stock, ledger and status histories are the audit trail.
  • Dropship (fulfillment = dropship, supplier portal), affiliates, reviews and abandoned-cart messages are planned, not built (carts.abandoned_notified_at exists for later).
  • Home feed does a full scan (~650 ms at 20k products); add cached min price/stock columns if the catalog grows.
  • The admin dashboard shows placeholders: there is no reports API yet.

৭. ডেটার প্রবাহ: প্রধান ফ্লো

অর্ডার দেওয়া (COD)

কার্ট→quote→place (idempotent)→অর্ডার + আইটেম→স্টক রিজার্ভ→ঝুঁকি যাচাই
  1. Quote: দাম হিসাব (base → সেল/ফ্ল্যাশ, সবচেয়ে কম) → অটো কুপন → সর্বোচ্চ ১টি টাইপ করা কোড → জোন থেকে ডেলিভারি চার্জ। কিছুই লেখা হয় না।
  2. Place, একটি ট্রানজ্যাকশনে: orders + order_items (ফ্রিজ স্ন্যাপশট), payments রো (method cod), order_status_history, স্টক reserved += qty ও stock_movements রো (order_reserve), কুপন redemption, ফ্ল্যাশ qty_sold। ক্লায়েন্ট কী-তে idempotent, তাই ডাবল ক্লিকে ডুপ্লিকেট হয় না।
  3. ঝুঁকি (RiskService): risk_score, risk_reasons (ফোন/IP/ডিভাইসে velocity, COD সীমার ওপরে, প্রথম গেস্ট অর্ডার) সেট করে এবং ঝুঁকিপূর্ণ হলে call_status = pending। অর্ডার কখনো আটকায় না।

অর্ডার স্ট্যাটাস

processing→partially_shipped→shipped→delivered→completed

পাশের স্টেট: on_hold, cancelled, pending_payment (অনলাইন পেমেন্টের আগে অব্যবহৃত)। on_hold/cancelled/pending_payment স্টাফ সরাসরি বসায়; processing → delivered শিপমেন্ট থেকে recompute() দিয়ে নির্ণীত হয়। delivered → completed রিটার্ন উইন্ডোর পর complete-orders জবে হয়। বাতিলে রিজার্ভ স্টক ফিরে আসে এবং কুপন ব্যবহার, ফ্ল্যাশ স্টক ও বাল্ক-কোড ব্যবহার রিভার্স হয়; শিপমেন্ট booked থাকলে বাতিল প্রত্যাখ্যাত।

শিপিং

স্টাফ অর্ডার লাইন থেকে শিপমেন্ট বানায় (ভাগ করা যায়) → pending → ready → কুরিয়ার বুক (অ্যাডাপ্টার courier_bookings-এ কাঁচা রিকোয়েস্ট/রেসপন্স লেখে, consignment_id বসায়) → handed_over → in_transit → delivered/failed/returning/returned। স্ট্যাটাস ওয়েবহুক বা sync-couriers জবে আসে এবং courier_status_events-এ (কাঁচা ও ম্যাপ করা) জমে। হ্যান্ডওভারে স্টক বের হয় (ship মুভমেন্ট: on_hand -= qty, reserved -= qty)। ডেলিভারি চার্জ প্রথম পাঠানো শিপমেন্টে বসে। অ্যাডাপ্টার: fake (কাজ করে), steadfast ও pathao (স্যান্ডবক্সে যাচাই হয়নি; কী আসে env থেকে, DB থেকে নয়)।

রিটার্ন ও রিফান্ড

requested → approved|rejected → pickup_booked → received → inspected → closed। ইন্সপেকশনে প্রতি লাইনের অবস্থা (resellable/damaged) বসে এবং রিস্টক হতে পারে (return_restock মুভমেন্ট)। প্রতি রিফান্ডে একটি refunds রো: লাইনপ্রতি অঙ্ক = (লাইন মোট − লাইন ডিসকাউন্ট) আনুপাতিক। returns.refundApprovalAboveP-এর ওপরে হলে needs_approval সেট হয় এবং refunds.approve পারমিশনওয়ালা অন্য স্টাফকে অনুমোদন দিতে হয়। রিফান্ড শুধু রেকর্ড হয় (এখনো পেমেন্ট গেটওয়ে বা ওয়ালেট লেজার নেই)।

SR (ফিল্ড সেলস) ও B2B

SR ক্রেতা দোকানের জন্য মেমো (sr_sales, স্ট্যাটাস submitted) বানায়, দাম SR-ই দেয়। অফিস স্টাফ অনুমোদন করে (স্টক রিজার্ভ, sr_reserve) বা বাতিল করে; ডেলিভারিতে স্টক বের হয় (sr_ship) এবং দোকানের বাকিতে sale_due লেজার রো যোগ হয়; আদায় SR রেকর্ড করে, স্টাফ confirm (বা reject) করে। Reversal reversal রো বসায় ও স্টক ফেরত দেয়। মাসিক sr_commissions = কনফার্ম হওয়া আদায় × হার (SR-এর ওভাররাইড বা সেটিং sr_default_commission_bp); কর্তন হলো sr_commission_adjustments।

ক্রয়

draft → sent (লাইন লক, সাপ্লায়ারকে ইমেইল) → partially_received → received, অথবা closed (বাকি ছেড়ে বন্ধ) / cancelled। গ্রহণে (purchase_orders.receive) প্রতি লাইনে ভালো ও রিজেক্ট পরিমাণ লেখা হয় (বাকির বেশি নয়)। শুধু ভালো পরিমাণ স্টকে যায় (po_receive মুভমেন্ট), variants.cost_p ওয়েটেড অ্যাভারেজে হালনাগাদ হয় (আগে/পরে po_receipt_items-এ থাকে) এবং supplier_ledger-এ receipt রো যোগ হয়। পেমেন্ট ও অ্যাডজাস্টমেন্ট আরও লেজার রো; ভুল reverse হয়, এডিট নয়।

প্রমোশন

দামের ক্রম: base → সেল বা ফ্ল্যাশ দাম (সবচেয়ে কম) → অটো কুপন (প্রায়োরিটি ক্রমে, পরস্পরের সাথে স্ট্যাক করতে হবে) → একটি টাইপ করা কোড (দ্বিতীয়টি তখনই যখন দুটোই স্ট্যাক অনুমতি দেয়) → ডেলিভারি ডিসকাউন্ট। ফ্ল্যাশের পরিমাণ আইটেম ও কাস্টমারপ্রতি সীমিত; কার্ট বেশি নিতে দেয় না (409 FLASH_LIMIT)। বাল্ক সেল variants.sale_* লেখে এবং পুরনো মান sale_batch_items-এ রাখে, যাতে “Undo” ফিরিয়ে দিতে পারে।
